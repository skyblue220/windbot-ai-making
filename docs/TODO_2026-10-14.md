## 탐색 트랙 — Card Knowledge Layer (결정 필요, 현재 v1 작업을 대체하지 않음)

배경: 카드 ID 목록 기반 Executor의 확장성 문제에서 출발해, 룰 엔진용 카드 데이터와 AI용 의미 데이터를 분리하는 계층을 구상 중이다.

코드로 확인한 사항:
- `cards.cdb`를 읽어 카드 정보 객체를 만드는 부분은 **이미 있다.** `NamedCardsManager.LoadDatabase()`가 `datas`와 `texts`를 조인해 `NamedCard`(이름, 텍스트, 레벨, 종족, 속성, 공수, 타입, setcode)를 만든다 (확인).
- 카드군 판정의 기반도 **이미 있다.** `setcode`를 cdb에서 읽고(확인), `ClientCard.HasSetcode(int)`가 있다 (확인). Lua 스크립트도 `c:IsSetCard(SET_RYZEAL)`로 같은 정보를 쓴다 (확인).
- `activationDescription`은 `(카드 코드 << 20) | 문자열 인덱스`로 인코딩되어 있다. 로그의 2건에서 `desc >> 20 == 카드ID`, 하위 20비트 0을 확인했다 (확인). **인덱스가 0보다 큰 경우는 미관측**이다.
- Lua 스크립트에서 효과 종류(`SetType`), 분류(`SetCategory`), 발동 이벤트(`SetCode`), 횟수 제한(`SetCountLimit`), 위치(`SetRange`)를 기계적으로 읽을 수 있다 (Ice, Duo Drive로 확인). 단 `Clone()`이나 헬퍼 함수로 만든 효과는 단순 정적 파싱으로 놓칠 수 있다 (추정).

작업 후보:
- [ ] **T1. 선행 연구·프로젝트 조사.** "카드 데이터와 AI 사이에 이 계층이 비어 있다"는 주장은 아직 검증되지 않았다. 교수님께 단정하기 전에 먼저 조사한다. (RL 기반 유희왕 에이전트 프로젝트들이 있는 것으로 기억하나 확인 필요)
- [ ] **T2. 파생 태그 PoC.** `ydk` 카드 ID → `NamedCard`의 종족·속성·레벨로 `PyroMonsters`, `ThunderMonsters`, `Level4Monsters`를 자동 생성하고, 현재 손으로 쓴 리스트와 diff로 검증한다.
  - 주의: `ClientField.Deck`은 ID 0 자리표시자이므로 실제 덱이 아니라 **덱 목록(ydk)** 에서 파생해야 한다 (확인).
  - P0의 "DeckProfile ↔ ydk 검증"과 같은 구조로 함께 해결할 수 있다.
- [ ] **T3. 효과 메타데이터 추출 PoC.** Ryzeal 13장의 Lua에서 (타입, 분류, 이벤트, 카운트 키)를 추출하고 정적 파싱의 커버리지를 측정한다. 실패하면 코어에서 `Effect.CreateEffect`를 계측하는 방법을 검토한다. 수작업 태그(starter/extender 등)는 이 자동 추출로 채울 수 없는 부분에 한정한다.
- [ ] **T4. 범위 결정.** Rust 클라이언트나 엔진 재작성은 현재 범위에서 제외하거나 후순위로 둔다. 카드 동작이 `ocgcore`의 Lua API에 묶여 있어, 새 엔진이 수천 장의 스크립트와 호환되어야 하기 때문이다 (추정).
- [ ] **T5. 상담용 질문을 좁힌다.** 예: "카드 의미 계층이 덱별 하드코딩 코드량과 새 덱 이식 비용을 줄이는가?" Swordsoul과 Ryzeal 두 덱 데이터가 있으므로, 이식 시 수정 줄 수와 자동 파생 태그의 커버리지를 측정 지표로 삼을 수 있다. (제안)
