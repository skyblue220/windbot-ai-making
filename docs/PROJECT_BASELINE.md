## 1. 프로젝트의 핵심

> 카드 효과의 의미와 현재 듀얼 상태를 표현하고, 행동과 그 결과로 생긴 상태 변화를 학습해, 카드 간 상호작용과 효과 순서에 따른 기대 가치를 판단하는 AI를 만든다.

### 1.1 핵심 연구 질문

> **같은 카드·같은 행동의 가치가 상태에 따라 달라진다는 것을 AI가 학습할 수 있는가?** (상태 기반 행동 가치 평가)

- 카드 효과 구조화, 상대 대응 평가, 다른 덱으로의 일반화는 이 질문을 받치는 기반 기술로 둔다. 각각 별도 연구 주제가 될 수 있지만, 지금은 하나의 결과로 묶지 않는다.
- 실험의 핵심 방식:

> 실제 엔진에서 동일한 상태를 반복 재현하고, 서로 다른 행동의 결과를 관찰하여, 상태에 따른 행동 가치를 학습한다.

### 1.2 방향

- **가치를 판단하는 주체는 AI다.** 카드 정보(cdb 수치, Lua 효과 의미)를 입력으로 받아 AI가 직접 판단한다. 사람이 만든 점수표(xlsx, `CardValueEngine`)와 역할 분류(`클래스 구분.txt`)는 출발점이 아니라 비교 기준이다.
- **학습 대상은 상태에 따른 행동 가치다.** 같은 Ext Ryzeal이라도 패의 Sword, 이미 쓴 소환과 효과, 남은 턴당 1번 효과, 상대의 Ash 가능성, 이어서 만들 수 있는 필드에 따라 가치가 달라진다.
- **방식**: 강화학습만으로 맨땅에서 배우게 하지 않는다. Lua 의미 추출과 실제 엔진 결과를 바탕으로 행동 이후 양쪽의 필드·묘지·패 자원 변화를 평가하고, 비용·리스크·리턴의 기댓값을 다룬다.
  - 초기에는 효과 사용 후 2~3수 정도의 전개를 평가하는 것을 목표로 한다. 탐색 깊이와 평가 방식은 실험으로 정한다.
  - "수"는 AI의 행동 횟수만이 아니라 상대의 대응과 체인 해결을 포함할 수 있으므로, 정확한 정의는 이후에 정한다.
- **학습 신호**: 승패뿐 아니라 행동 전후의 상태 변화, 자원 증감, 상대의 대응, 최종 필드의 질, 다음 턴에 남는 자원도 신호로 쓴다.
- **새 봇은 기존 Executor와 구조가 완전히 다르다.** 기존 `RyzealExecutor`는 "순서가 아니라 점수로 행동을 고르는 방식도 작동한다"는 것과 Executor의 작동 방식을 시험한 검증용 구현이었고, 그 의미는 구현으로 끝났다. 새 봇은 카드별 판단 함수(`AddExecutor`, `Can*`/`Commit*`), 카드 ID 목록, 점수표를 쓰지 않는다. 기존 Executor의 선택은 학습 정답으로도, 실험 진행 정책으로도 쓰지 않는다.
- **성공 기준**: Ryzeal 승률이 아니라, 학습한 판단 방식이 다른 상태와 다른 카드에도 통하는지가 기준이다. 범위는 Ryzeal → 유희왕 전반 → Lua 의미 분석 → 다른 카드게임(예: Slay the Spire) 순으로 넓힌다.
- **Ryzeal은 일부러 고른 쉬운 덱**이다. 헷갈리는 효과가 없는 첫 실험 대상이다.

## 2. 데이터 계층

AI가 판단에 쓰는 정보를 세 계층으로 나눈다. 핵심은 **변하지 않는 카드 규칙**과 **이번 듀얼에서 실제로 일어난 일**을 섞지 않는 것이다.

| 계층 | 담는 것 | 변하는가 | 정보의 기준 |
|---|---|---|---|
| 카드 지식 DB | 카드의 기본 정보, 효과의 조건·비용·대상·처리·제약 | 카드가 바뀌지 않는 한 고정 (정보는 점진적으로 보완) | cdb, Lua, 검증된 기여 |
| 듀얼 상태 | 패·필드·묘지·제외·엑스트라, 효과별 발동·사용 기록, 현재 체인 | 듀얼마다, 매 이벤트마다 변함 | 엔진 이벤트 |
| AI 판단 | 행동별 예상 결과, 기대 가치 | 판단할 때마다 계산 | 위 두 계층 + 평가 모델 |

### 2.1 카드 지식 DB

- **카드 하나당 레코드 하나.** cdb와 Lua에 흩어진 정보를 한 곳에 모은다. 나중에 Rust로 카드를 정의할 때의 명세로도 쓸 수 있게 한다.
- **효과 단위로 기록**: 발동 조건, 비용, 대상, 처리 내용, 카드 이동, 특수 소환, 발동 위치, 다른 카드·상태와의 의존성, 사용 제약.
  - 예: `Duel.SpecialSummon`이 있다는 사실만으로는 부족하다. 무엇을, 어디서, 어떤 조건으로 소환하는지, 소환 후 어떤 제약이 생기는지, 다음 행동에 어떤 영향을 주는지가 필요하다. 이 표현 방식이 프로젝트의 핵심 연구 문제 중 하나다.
  - 범용 Lua 분석기를 처음부터 만들지 않는다. 실험에 쓰는 카드부터 정확하게 표현한다.
- **사용 제약은 "언제 세고, 언제 되돌리고, 언제 초기화하는지"의 규칙으로 저장한다.** 사용 여부 값(`effectUsed`)은 카드 DB에 넣지 않는다. 그 값은 듀얼 상태에 속한다.
- **use와 activate를 구분한다.** 발동이 무효됐을 때 다시 쓸 수 있는지가 다르다. 제약의 범위(카드명 기준인지 효과별인지, 턴 단위인지 듀얼 전체인지)도 함께 기록한다.
  - 이 구분은 상당 부분 Lua에 이미 있다. 기준 덱 Ryzeal 몬스터 5장은 룰 특수소환이 모두 `SetCountLimit(1,id,EFFECT_COUNT_CODE_OATH)`, 발동 효과가 모두 `SetCountLimit(1,{id,1})`다 (확인).
  - **엔진에서 확인 (2026-11-07)**: Mist Valley Apex Avian(발동 무효)으로 Bonfire("1턴에 1장밖에 **발동**할 수 없다", OATH)를 막은 뒤 Bonfire를 다시 발동할 수 있었다 (확인).
    - "발동" 제약(OATH): 발동 무효되면 횟수를 돌려받아 다시 발동 가능. 효과 무효는 소비.
    - "사용" 제약(OATH 없음): 발동 무효·효과 무효 모두 소비되어 다시 사용 불가.
    - 듀얼 상태 계층은 이 규칙대로 처리한다 (커밋 `e18b72e`).
- **정보마다 출처와 확실성을 기록한다.**

| confidence | 의미 |
|---|---|
| `unknown` | 아직 모름 |
| `inferred` | Lua나 텍스트에서 추론 |
| `community_reported` | 사람이 입력 (사용자 기여) |
| `verified` | 실제 듀얼에서 엔진 결과와 일치함 |

- **사용자 기여는 Lua로 알 수 없는 부분에만 쓴다.** 출처·확실성 필드만 처음부터 두고, 여러 사람이 기여하는 체계는 덱을 넓힐 때 만든다.

### 2.2 듀얼 상태

- **엔진 이벤트에서 만든다.** AI가 "내가 썼다"고 스스로 기록하지 않는다.

```
엔진 이벤트 (발동 / 발동 무효 / 효과 무효 / 처리 완료)
   + 카드 지식 DB의 제약 규칙 (OATH 여부, 카운트 키, 범위)
   → 듀얼 상태의 발동·사용 기록 갱신
```

- WindBot은 체인 관련 엔진 메시지(`Chaining`, `ChainNegated`, `ChainDisabled`, `ChainSolved`)를 이미 받는다 (확인). 턴당 1번 사용 여부 자체는 엔진이 클라이언트에 알려주지 않으므로, 이 계층이 필요하다.
- 하나의 `use_count`로 압축하지 않는다. 효과마다 발동 시도, 발동 무효, 효과 무효, 정상 처리를 이벤트로 남기고, 사용 횟수는 카드 DB의 규칙에 따라 갱신한다.
- 기존 Executor의 `_activateEffectUsedThisTurn`, `_specialSummonEffectUsedThisTurn`은 AI가 스스로 기록하는 방식이었다. 새 봇은 이 방식을 쓰지 않는다.

### 2.3 엔진을 정답 판정기로 쓴다

- 카드 DB와 듀얼 상태로 "이 효과는 지금 쓸 수 있다"고 예측한 것을, 엔진이 실제로 준 합법 행동과 매번 비교한다.
  - 일치하면 그 레코드를 `verified`로 올린다.
  - 다르면 DB 오류이거나 아직 모르는 규칙이 있다는 뜻이다. 이 불일치 자체를 기록한다.

### 2.4 경계

- 이 계층은 **평가에 필요한 제약과 자원 변화의 근사**까지만 다룬다.
- **실제 효과 처리와 진짜 상태의 기준은 계속 엔진이다.** 효과 처리 전체를 흉내 내기 시작하면 사실상 엔진 재구현(Rust 재작성)이 되므로, 그 선을 넘지 않는다.

## 3. 판단 구조 (개념)

아래는 목표 구조이며 구현된 기능이 아니다.

```
엔진 이벤트 → 듀얼 상태 갱신 (카드 지식 DB의 규칙 적용)
   ↓
상태 표현 (듀얼 상태 + 카드·효과 표현)
   ↓
합법 행동 후보 (엔진이 보장)
   ↓
행동별 결과 예측 → 후속 행동과 상대 대응 탐색
   ↓
결과 상태의 가치 평가 → 행동별 기대 가치 비교
   ↓
행동 선택 → 엔진에서 실제 실행
   ↓
실제 상태 변화·상대 응답 관찰 → 로그 → 예측과 비교해 평가 모델과 카드 DB 검증
```

- **역할 분담**: 합법 행동과 실제 효과 처리는 엔진이 보장한다. AI는 그중 무엇을 고를지 판단한다.
- **행동 가치 (개념)**: `Q(s,a) = E[R(s,a) + γ·V(s')]`. 상태 가치 V를 학습할지, 행동 가치 Q를 직접 학습할지, 둘을 조합할지는 정하지 않았다.
- **숨겨진 상대 패 (개념)**: 상대의 가능한 응답 o마다 가치를 평가하고 가능성으로 평균 낸다. `Q(s,a) = Σ P(o|s)·Q(s,a,o)`.
- **탐색은 단계적으로 넓힌다.** MCTS를 처음부터 구현하지 않는다. 카드 표현과 상태 추적이 불완전한 상태에서 탐색을 키우면 잘못된 상태를 더 많이 탐색하게 된다.
  1. 상대 대응이 없는 상황에서 AI 행동 2~3개 평가
  2. Ash Blossom 등 제한된 상대 대응 추가
  3. 상대 응답의 확률적 평가
  4. 필요하면 MCTS 등 탐색 기법 검토

## 4. 실험 설계 원칙

### 4.1 반복 가능한 시작 상태로 행동을 비교한다

```
고정된 시작 상태 S
    ├─ 행동 A → 실제 엔진 실행 → 종료 필드 A
    ├─ 행동 B → 실제 엔진 실행 → 종료 필드 B
    └─ 행동 C → 실제 엔진 실행 → 종료 필드 C
                         ↓
                 결과 상태 가치 평가 → 행동 가치 학습
```

- 행동 결과를 예측하는 모델(forward model) 없이, 실제 엔진이 만든 결과로 행동 가치의 학습 신호를 얻는다.
- 결과 상태의 가치 자체는 여전히 평가해야 한다. 다만 이것은 가상 상태를 만드는 문제와는 별개다.
- **첫 행동만 바꾼 비교와 이후 정책까지 통제한 비교를 구분한다.** 첫 행동에 따라 이후에 고를 수 있는 행동이 달라지기 때문이다.
  - 첫 행동 이후의 진행도 새 봇이 맡는다. 초기에는 합법 선택지 중 무작위로 고르거나, 학습 중인 모델이 직접 고른다. 어느 쪽이든 진행 정책을 기록에 남긴다.
- **반복 가능한 시작 상태를 만드는 수단은 아직 확정되지 않았다.** 후보:
  - 봇이 방을 만들 때 `CreateGameInfo.dontShuffleDeck`로 덱을 섞지 않는 방 (옵션 존재는 확인, 시작 패 고정 여부는 미확인)
  - EDOPro 퍼즐 모드 (`puzzles` 폴더 있음, 확인. 퍼즐 모드에서 봇이 행동할 수 있는지는 미확인)
  - 어느 것도 구현 전제로 쓰지 않는다.

### 4.2 첫 실험: 선공 1턴 전개

- 평가 시점이 "턴 종료 시 필드"로 명확하고, 선공 첫 턴은 상대의 일반적인 효과 발동이 없다.
- **상대 대응 없는 실험과 Ash 대응 실험을 분리한다.** Ryzeal 자체의 전개 가치 학습과 Ash의 영향 학습을 섞지 않기 위해서다.
  - 1차: 상대 핸드트랩이 없다고 가정
  - 2차: 상대가 Ash를 보유한다는 조건을 명시 (상대의 시작 패와 덱을 통제할 수 있게 된 뒤)
- **P1 카드 범위**: Ext Ryzeal, Sword Ryzeal, Ice Ryzeal. 결과로 나오는 카드는 Detonator, Duo Drive.

## 5. 실행 환경

- **기준 환경은 WindBot과 EDOPro**다. 저장소는 `WindBot-Git`의 `ryzeal-development` 브랜치다.
- **WindBot에서 쓰는 것은 엔진 연결부뿐이다.** (자세한 흐름은 `WINDBOT_DATA_FLOW.md`)

```
EDOPro (엔진) ↔ TCP ↔ YGOSharp.Network ↔ GameBehavior (패킷 해석, 듀얼 상태 갱신, 응답 인코딩)
                                              ↓ 선택 요청마다 호출
                                         [GameAI 자리] ← 새 봇의 판단 계층이 들어가는 곳
```

  - 유지: EDOPro가 봇 프로세스를 띄우는 방식, 네트워크, `GameBehavior`의 패킷 해석과 응답 인코딩.
  - 교체: `GameAI`와 그 아래의 Executor 전체. 새 판단 계층은 약 20종의 선택 요청(메인 페이즈 행동, 체인, 효과 발동 여부, 카드·대상 선택, 선언 등)을 카드별 코드 없이 같은 경로로 처리한다.
- **Rust 재작성은 후순위 선택지**다. 고려하는 이유:
  1. 카드 정보가 cdb와 Lua에 나뉘어 있어서, AI가 카드를 이해하려면 여러 파일을 오가야 한다. 그래서 Executor가 카드 목록을 코드에 직접 적어 넣어 왔다.
  2. 기존의 메시지 기반 구조에서는 행동을 가상으로 실행하고 상태를 복제해 여러 수 앞을 탐색하는 작업이 비효율적이다.
  3. Lua 스크립트 작성 방식이 난잡해서 기존 카드와 상호작용할 때 버그가 자주 생긴다.
- **지금 작업은 나중의 이전을 막지 않게 한다.** 카드 지식 DB는 엔진과 독립된 형식으로 만들고, AI 판단 코드는 "상태와 합법 행동을 받아 행동 하나를 돌려준다"는 경계만 갖는다.

## 6. 현재 구현 상태

- **새 봇**: 아직 없다. 판단 계층, 듀얼 상태 계층, 카드 지식 DB 모두 미착수다.
- **기존 봇 (검증 종료)**: `RyzealExecutor`는 엔진이 준 합법 행동에서 후보를 만들고 임시 점수로 골라 실행하는 구조로, 실제 듀얼에서 작동함을 확인했다. 더 개발하지 않는다.
  - 남은 결함(예: Detonator / Duo Drive 소환 시 장착 효과가 거절됨)은 기존 봇의 기록으로만 남기고 고치지 않는다.
- **로그**: 기존 봇이 남긴 JSONL 로그는 기존 봇의 판단 기록이다. 새 봇의 학습 데이터로 쓰지 않는다. 다만 로그 형식(메인 페이즈 판단, 합법 행동, 선택, 예/아니오 질문)은 새 봇 기록 설계의 참고 자료다.
- **덱**: `ProjectIgnis\deck\AI_Ryzeal.ydk`를 기준으로 통합했다(`3f461c1`). 봇이 실제로 읽는 `Windbot\Decks\AI_Ryzeal.ydk`도 같은 내용이다.

## 7. 작업 순서

단계마다 다음 단계를 염두에 두고 설계한다. 상태 전이 기록과 카드 효과 표현은 서로를 결정하고, 엔진 비교 검증(2.3)으로 연결된다. 다만 37장 전체를 먼저 완성하지 않고, **작은 범위로 전 과정을 한 번 관통한 뒤 넓힌다.** 각 부분이 서로의 완성을 기다리는 상황을 피하기 위해서다.

| 단계 | 핵심 목표 | 완료 기준 |
|---|---|---|
| P0 | 새 봇 골격 | `GameAI` 자리에 새 판단 계층의 진입점을 두고, 모든 선택 요청에 기존 Executor 없이 응답하며 듀얼을 끝까지 진행 |
| P1 | 수직 프로토타입 | 카드 3장(+결과 카드)으로 상태 기록부터 가치 평가까지 관통 |
| P2 | 카드 지식 확장 | 기준 덱 37장의 효과 표현과 엔진 비교 검증 |
| P3 | 탐색과 일반화 | 상대 대응, 확률적 평가, 다른 덱 적용, Rust 이전 검토 |

### P1 완료 조건

P1의 목표는 "AI가 잘 플레이한다"가 아니라, **AI가 상태를 입력받고, 행동을 평가하고, 실제 엔진 결과로 평가를 개선할 수 있는가**다.

1. 고정된 시작 상태를 반복해서 재현할 수 있다.
2. 엔진의 합법 행동을 기록할 수 있다.
3. 첫 행동을 통제한 여러 실험을 실행할 수 있다.
4. 행동 이후의 실제 엔진 상태를 기록할 수 있다.
5. 턴 종료 시 필드와 자원 변화를 비교할 수 있다.
6. 행동별 결과를 이용해 최소한의 가치 평가 모델을 학습할 수 있다.
7. 학습 모델이 같은 행동을 상태에 따라 다르게 평가하는 사례를 확인할 수 있다. (성능 향상이 아니라, 핵심 연구 질문에 대한 첫 증거를 확인하는 단계)

## 8. 아직 정해지지 않은 것

- 카드 효과를 모델에 넣는 방식: 구조화 속성, 그래프·순서 표현, 자연어 텍스트 사용 여부
- 카드 지식 DB의 저장 형식과 스키마 세부
- 모델 구조와 학습 알고리즘 (V, Q, 또는 조합)
- 결과 상태(턴 종료 필드)의 가치를 평가하는 기준, 승패와 최종 필드 가치를 결합하는 방식
- 반복 가능한 시작 상태를 만드는 수단 (`dontShuffleDeck`, 퍼즐 모드 등)
- `GameBehavior`가 AI를 거치지 않고 자동 응답하는 경우를 그대로 둘지 (`WINDBOT_DATA_FLOW.md` 4.1)
- 새 봇이 덱(ydk)을 지정하는 방식 (지금은 Executor의 덱 이름으로 정해짐)
- 기존 Executor를 새 봇의 대전 상대로라도 남길지
- 탐색 깊이와 "수"의 정의
- 대량 대전 수단: 기존 프로젝트를 쓸지, 직접 만들지
- 사용자 기여 체계를 언제, 어떤 검증 절차로 열지

## 9. 작업 원칙

- 요청 범위 안에서 작업하고, 로그를 받았다고 임의로 디버깅까지 나가지 않는다.
- 확인하지 않은 구현 상태나 원인을 사실처럼 적지 않는다.
- 진짜 상태의 기준은 엔진이다. AI 쪽 기록은 엔진 이벤트에서 만들고, 엔진 결과로 검증한다.
- 설계를 키우기 전에 작은 범위로 실제로 학습·평가되는 구조를 먼저 만든다.
- 새 봇은 기존 Executor 구조 위에 짓지 않는다. 기존 Executor를 고치거나 검증하는 일을 다음 작업으로 잡지 않는다.
- `아르스 카드 스크립트 수정` 폴더는 이번 작업과 무관하므로 제외한다.
