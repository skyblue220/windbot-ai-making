## 이 문서의 전제

- 핵심 연구 질문: **같은 카드·같은 행동의 가치가 상태에 따라 달라진다는 것을 AI가 학습할 수 있는가?**
- 핵심 방식: 실제 엔진에서 동일한 상태를 반복 재현하고, 서로 다른 행동의 결과를 관찰하여, 상태에 따른 행동 가치를 학습한다.
- **새 봇은 기존 Executor와 구조가 완전히 다르다.** 기존 `RyzealExecutor`는 검증용 구현으로 역할을 마쳤다. 고치거나 검증하지 않고, 학습 정답이나 실험 진행 정책으로도 쓰지 않는다.
- WindBot에서 쓰는 것은 엔진 연결부(프로세스 실행 방식, 네트워크, `GameBehavior`의 패킷 해석과 응답 인코딩)뿐이다. 새 판단 계층은 `GameAI` 자리에 들어간다.
- 작은 범위로 전 과정을 한 번 관통(P1)한 뒤 넓힌다(P2).
- Rust 재작성은 후순위이며, 지금 작업이 나중의 이전을 막지 않게 한다.

- [x] **선택 요청 공통 표현.** 21종 요청을 `RequestKind` + 선택지 목록 + 제약으로 표현하고, 응답 형태를 5가지 `RequestShape`(One, Many, Sum, Counter, Order)로 나눴다. 메인 페이즈 행동, 체인, 효과 발동 여부, 카드·대상 선택, 합계 선택, 카운터, 존, 표시 형식, 정렬, 선언, 가위바위보, 선후공까지 같은 경로로 처리한다.

- [ ] `activationDescription` 인코딩 확인: `(카드 코드 << 20) | 문자열 인덱스`. 인덱스 0은 확인했고 0보다 큰 경우는 미관측 (확인).
- [ ] 사용자 기여 체계는 만들지 않는다. 출처·확실성 필드만 유지한다.

### 듀얼 상태와 검증
- [ ] 듀얼 상태 계층을 37장으로 확장. 효과마다 발동 시도, 발동 무효, 효과 무효, 정상 처리를 이벤트로 남기고, 하나의 `use_count`로 압축하지 않는다.
- [ ] 엔진 비교 검증을 37장으로 확장. 일치하면 `verified`, 불일치는 따로 기록한다.
- [ ] **경계**: 평가에 필요한 제약과 자원 변화의 근사까지만 다룬다. 효과 처리 전체를 흉내 내지 않는다.

### 상태 전이 기록 확장
- [ ] LP, 턴 종료 시 상태, 듀얼 결과(승패, 종료 턴).
- [ ] 카드 인스턴스 구분 정보(위치, 표시 형식, 엑시즈 소재).
- [ ] 상대 정보는 공개된 것만 상태에 넣는다 (비공개 정보 필터링).
- [ ] 대량 대전 수단 조사: 새 봇끼리 자동 대전(봇이 방을 만드는 `CreateGame` 경로 포함), 또는 ocgcore를 직접 쓰는 기존 프로젝트. (제안)

## 정해지지 않은 것

- 카드 효과를 모델에 넣는 방식: 구조화 속성, 그래프·순서 표현, 자연어 텍스트 사용 여부
- 카드 지식 DB의 저장 형식과 스키마 세부
- 모델 구조와 학습 알고리즘 (V, Q, 또는 조합)
- 결과 상태(턴 종료 필드)의 가치 평가 기준, 승패와 최종 필드 가치의 결합 방식
- 반복 가능한 시작 상태를 만드는 수단 (`dontShuffleDeck`, 퍼즐 모드 등)
- `GameBehavior` 자동 응답을 그대로 둘지
- 새 봇이 덱(ydk)을 지정하는 방식
- 기존 Executor를 새 봇의 대전 상대로라도 남길지
- 탐색 깊이와 "수"의 정의 (AI 행동 횟수만인지, 상대 대응과 체인 해결을 포함하는지)
- 대량 대전 수단: 기존 프로젝트를 쓸지, 직접 만들지
- 사용자 기여 체계를 언제, 어떤 검증 절차로 열지

## 하지 않는 것 / 후순위

- **기존 Executor 개발·수정·검증**: `RyzealExecutor`의 결함(예: Detonator / Duo Drive 소환 시 장착 효과 거절), 점수 튜닝, 카드 구현 검증, HOPT 보조 추적 정리. 검증용 구현으로 역할을 마쳤다.
- **기존 Executor의 선택을 학습 정답이나 실험 진행 정책으로 쓰는 것.**
- **기존 봇의 로그를 학습 데이터로 쓰는 것.** 로그 형식만 참고한다.
- **처음부터 MCTS 구현**: 카드 표현과 상태 추적이 불완전한 상태에서는 하지 않는다.
- **Rust 재작성**: 후순위. 이유는 cdb·Lua 분리, 메시지 기반 구조에서의 다수 수 탐색 비효율, Lua 스크립트 작성 방식의 상호작용 버그.
- 외부 Executor DLL 경로 (Stage 01 Probe는 빌드·로딩 미검증)
